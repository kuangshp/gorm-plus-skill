# 代码生成

开发业务接口时先执行 [默认接口开发流程](interface-workflow.md)：根目录 `generator.go` → 日期 SQL → 按项目配置同步数据库 → 运行生成入口 → 注入 Repository。这里只补充生成器的检查与覆盖行为。

## 先检查，后执行

读取根目录 `generator.go`、Makefile/脚本、配置和本地模板；缺少入口时按默认流程创建，确认：

- 使用哪个数据库与 schema；不要把密码或连接串抄入日志和交付资料。
- 当前表名、主键和所需业务接口；数据库结构是否已按项目流程同步。
- DAO、Model、Repository、API、Mapper 等实际输出位置。
- 模板来自项目本地还是库内嵌；goctl 的模板来源也需要单独核对。
- 所有交互输入的含义及空输入的行为；只生成已确认的目标表。

库的入口可从 `gormplus_generator.go` 追到 `generator/config.go` 与 `generator/generator.go`。项目已经有生成入口时优先使用项目入口，不额外搭建另一套。

## Model 输出目录约束（强制）

- `query/model` 是生成器专属目录，包括所有子目录及所有文件；若项目将 Model 输出到其他路径，以 `ModelPkgPath` 等真实配置定位并应用同一约束。无论文件是否带 `.gen.go` 或生成标记，都禁止手写内容、手动修改和手动新建文件。
- 禁止手工增删改实体字段、类型、标签、注释、表名映射或方法；禁止复制、拆分、重命名实体来新建文件，也不能在该目录增加 `extra.go`、`custom.go` 等扩展文件。使用补丁、脚本、格式化或复制命令直接修改生成产物同样属于手工修改，不能用作绕过方式；必要的输出格式调整应交给生成流程。
- 新增表或字段变更先修改日期 SQL、同步并核对表结构；类型映射、标签或输出格式问题修正实际生成配置/模板；随后运行根目录生成入口，检查对应 Model 的生成差异。仅参数或模板变化不需要伪造表结构变更，接口开发仍遵循默认流程。
- 缺少实体或生成失败时，修复输入、配置、模板或生成流程，不能先手写实体让代码通过编译。现有业务 DTO/VO 及响应投影按其实际层级定义，不放入 Model 输出目录，也不复制一套持久化实体替代生成结果。
- 完成时核对 Model 目录的每项变更均来自实际生成结果，不能仅凭文件名或生成注释声称已生成。此目录不适用 Repository 已有非生成文件允许扩展方法的规则。

## 覆盖行为必须核对源码

基线实现中：

| 产物 | 已有文件的处理 |
| --- | --- |
| Repository `_gen.go` | `writeFileAlways`，覆盖 |
| Repository 自定义扩展 `.go` | `writeFileIfNotExist`，保留已有文件 |
| 表对应 API `.api` | 已存在时跳过 |

DAO/Model 由 gorm-gen 路径生成，其他产物按各自分支处理，必须检查实际输出和差异。不要根据 README 中概括的“Repository 不覆盖”推断 `_gen.go` 也会保留。

Repository 新文件只能由项目生成器生成，禁止手动创建或复制生成结果作为替代。自定义方法写入对应的已有非生成文件；该文件缺失时，修复配置或模板并运行目标表生成，不能手写补齐。

字段变化后，重新运行生成器不代表已存在的 API、扩展文件、Handler 和 Logic 都已更新。goctl 对已有文件的行为也应按当前版本核实。

## 生成任务流程

1. 按当前项目要求确认业务操作、筛选字段、响应字段和最终接口清单。
2. 先完成项目规定的 SQL/迁移与结构同步，再运行项目生成入口。若步骤失败，先定位失败原因；不要跳过或手写替代产物。
3. 检查日志及实际文件，防止某个文件生成失败但整体命令仍结束。
4. 基于生成产物按业务裁剪 API，并接入项目聚合入口；go-zero 项目执行 API validate 后重新生成下游 Types、路由、Handler 和 Logic。
5. 模板缺少标准生成能力或格式不符合项目要求时，修正实际使用的模板并重生成；Repository 模板只处理数据访问能力，不能加入业务校验或流程。不能在生成文件上手工补完后宣称可复现。
6. 保留模板已有的接口与实现嵌入及构造函数，先复用默认方法、Wrapper 和选项，禁止改名重复定义 CRUD。确认现有能力无法表达的数据访问操作，才在对应的已有非生成文件中增加方法，同步维护对应的已有接口定义并说明能力缺口；不能手动新建文件。业务校验和流程编排放在 Logic/Service，禁止为此覆盖默认 CRUD 或修改模板注入业务规则。
7. 按项目要求在独立临时目标用相同版本、输入、配置和模板重生成，比较目标产物。保护已有手写实现，不为验证直接删除工作区文件。

## 配置定位

常见键包括 `out_path`、`model_pkg_path`、`repo_path`、`api_path`、`api_mapper_path`、`proto_mapper_path` 和 `goctl_template_home`，具体支持情况以当前 `generator/config.go` 为准。

不要假定所有模板都能通过同一个配置项覆盖；追踪当前生成入口如何定位模板。更新依赖库内嵌模板涉及库发布/依赖变更，先确认是否属于任务范围。

来源和核对基线见 [来源与验证场景](verification.md)。
